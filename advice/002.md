UAV ISAC 系统深度审计报告
一、通信模块优化点
1.1 有限块长反解存在重复计算（physical/finite_blocklength.py)

minimum_blocklength_normal_approximation 和 minimum_snr_normal_approximation 使用倍增+二分搜索，每次迭代都重新调用 awgn_capacity_bits_per_use 和 awgn_dispersion_bits2_per_use，重复计算 log2(1+γ) 和 (1+γ)^-2。

python

# finite_blocklength.py:96-110 当前：每次二分都重算 capacity/dispersion
while high < maximum and achievable_information_bits(snr_linear, high, target_bler) + 1e-12 < bits:
    high = min(maximum, 2 * high)


优化：capacity/dispersion 只依赖 SNR，在搜索外层计算一次，将 achievable_information_bits 内联为闭包，消除 ~80% 的 log2 调用。

1.2 通信链路预算未向量化（environment/communication.py)

InterUAVCommunicationModel.transmit() 对每条链路逐条计算 SNR/BLER/时延，K=4 UAV 时有 K(K-1)=12 条链路，每帧都跑 Python 循环。在 env_core.step() 的 2184 行巨型方法内，这是 per-frame 热点。

优化：将 SNR/BLER/时延计算向量化为 (K,K) 矩阵运算，用 np.log2 和 ndtr 的数组接口替代逐条标量调用。

1.3 缺少 AMC 与 HARQ 机制

当前通信只用有限块长正常近似（解析 BLER），未建模自适应调制编码（AMC）和混合自动重传（HARQ）。在低 SNR 区间，固定编码率导致可达比特数被低估。

优化（若需扩展）：在 finite_blocklength.py 增加 MCS 码本表 + HARQ IR-chase 组合，按 SNR 区间选择最优 MCS。但这属于功能扩展，非纯优化。

二、感知模块优化点
2.1 Deflection 慢速路径仍是三重 Python 循环（physical/deflection.py:320-382)
python

for i in tx_indices:          # K
    for j in rx_indices:      # K
        for q in range(Q):    # Q
            d_raw = compute_raw_deflection(...)  # 标量
            g_dd = compute_dd_effectiveness(...)  # 标量 sinc


当 use_report_link=True 或 use_swerling=True 时走此路径。K=4, Q=2 时约 24 次迭代，但 compute_dd_effectiveness 内部又调用 compute_dd_misalignment → 两次 np.round + 两次 np.sin，标量 dispatch 开销显著。

优化：几何已向量化（tau/nu/alpha 是 (K,K,Q) 数组），可将 g_dd 和 d_raw 也用 compute_dd_phys_gain_batch 一次性算完，仅在 Swerling 衰落处保留标量 RNG 抽取。预期将该路径加速 3-5x。

2.2 OTFS 模糊增益存在标量/批量双实现（physical/otfs.py)
compute_dd_phys_gain（标量，行 121）→ 调 compute_dd_unambiguous_support + compute_dd_ambiguity_gain
compute_dd_phys_gain_batch（向量化，行 146）→ 一次性算完

但 deflection.py 的慢速路径（行 360）调用的是标量版本，而快速路径（行 289）自己内联了 sinc 计算。两处逻辑重复。

优化：统一调用 compute_dd_phys_gain_batch，删除 deflection.py:289-302 的内联 sinc，消除逻辑分叉。

2.3 检测概率重复计算 Q^-1(P_FA)（utils/math_utils.py:46)
python

def compute_PD(D_q, P_FA, eps=1e-10):
    q_inv = Q_inverse(np.array(P_FA))  # 每次调用都算 erfinv
    sqrt_D = np.sqrt(np.maximum(D_q, eps))
    return Q_function(q_inv - sqrt_D)


P_FA 通常是全局常量（0.001），但 compute_PD 每次都调 erfinv。在 inner_solver.py 的贪心循环中，marginal_utility_gain_batch 每轮迭代都触发此计算。

优化：用 functools.lru_cache 缓存 Q_inverse(P_FA)，或在 InnerSolver.__init__ 中预计算 q_inv = Q_inverse(P_FA) 并传入。

2.4 证据融合 4 套模式共存（physical/evidence.py, 1113 行)

DETECTION_FUSION_MODES = {legacy_global, central_oracle, local_only, u2u_distributed}，4 种模式各有独立实现路径，维护成本高，且 legacy_global 与 local_only 在退化情形下数值不完全一致。

优化：将 4 种模式统一为 "融合拓扑图 + LLR 求和" 的单一引擎，用拓扑配置区分行为。删除 legacy_global（已被 local_only 取代）。

三、计算模块优化点
3.1 P0 贪心算法非子模，无近似保证（physical/inner_solver.py)
python

# inner_solver.py:14-18 文档已明确标注
# Utility: U_q(D_q) = -log(1 - P_D(D_q)), monotone INCREASING but NOT concave in D_q
# Hence F(S) is NOT submodular and the greedy is a HEURISTIC with no (1-1/e) guarantee.


当前效用 U=-log(1-P_D) 在 D 上经验非凹（U''>0 over 99.6% range），边际效用递增，贪心可能过度集中资源于少数目标。

优化：切换为饱和效用 U(D) = 1 - exp(-kD)（凹且单调），恢复子模性，贪心获得 (1-1/e)≈63% 保证。k 可按 P_D_min=0.8 对应的 D 标定。这是正确性+性能双赢的改动。

3.2 贪心主循环 O(|S|·|E|) Python 遍历（inner_solver.py:232-287)
python

while True:
    for candidate_index, e in enumerate(candidates):  # |E| 次 Python 迭代
        if key in selected: continue
        if ...: continue  # 约束检查
        if weighted_gain > best_gain: ...


虽有 refresh_target_scores 的 target-local batch 优化，但约束检查和 argmax 仍是 Python 循环。K=4, Q=2 时 |E|≈24 尚可，但规模增大时成为瓶颈。

优化：将约束检查向量化为布尔掩码，用 np.ma.masked_array + argmax 替代 Python 循环。候选集用 numpy 结构化数组而非 List[DeflectionEntry]。

3.3 max-min 功率求解 5 套实现并存（coordination/maxmin_power.py, ~1640 行)
实现	用途
solve_fixed_structure_maxmin_power_lp	部署路径（scipy.linprog）
replicated_local_row_maxmin_power	复制行本地
distributed_dual_maxmin_power	分布式对偶
distributed_column_generation_maxmin_power	列生成
local_transmitter_range_minimax_share	极小极大分享

部署只走第 1 套，其余 4 套为研究专用但未隔离，增加维护和测试成本。

优化：将研究实现移至 coordination/research/ 子包，coordination/__init__.py 只导出部署路径的 solve_fixed_structure_maxmin_power_lp。

3.4 capability_gauge SLSQP 静默失败（coordination/capability.py)
python

# capability_gauge 不查 res.success，失败静默返回末迭代/NaN


SLSQP 在约束不可行或数值病态时返回 res.success=False，但当前代码不检查，导致 NaN/错误结果流入下游功率分配。

优化：增加 if not res.success: raise CapabilityGaugeFailure(res.message)，或返回 Optional[float] 由调用方决定回退策略。这是正确性风险，优先级高。

3.5 env_core.py 巨型聚合器（11182 行，step() 2184 行)

六个子系统（配置校验/step 编排/协议收发/运动控制/功率协调/状态序列化）耦合在一个类里，step() 单方法 2184 行，__init__ 1622 行。这是最大技术债，导致：

单元测试无法隔离（只能端到端）
状态漂移（get_state/set_state 缺 5 个字段）
任何修改的回归风险极高

优化：按项目已规划的 P3 路线拆分为：

ProtocolTransportLayer（协议收发）
MovementController（运动+几何）
PowerAllocationLayer（功率协调）
StateSnapshot（序列化）
EnvCore（仅保留 step 编排，<300 行）
3.6 feasibility_oracle MILP+LP 交替组合爆炸（physical/feasibility_oracle.py, 1819 行)

Oracle 作为教师/上界基准，MILP 对选择 + LP max-min 功率交替。文档提及 "333 次 exact feasibility 调用"，单次 episode 的 Oracle 调用可能占训练时间的 30%+。

优化：

短期：加 MILP 超时 + LP 热启动（scipy.linprog 的 x0 参数）
长期：用 LP 松弛 + 随机舍入替代 MILP，牺牲少量上界紧度换 10x 加速

五、总结

物理层（physical/）质量最高，无状态函数、解析闭合、文档完善，上述 P0-P1 优化均为局部改动，风险可控。

最大结构性问题在 env_core.py（11182 行）和 trainer.py（7900 行），但项目已有 P0-P4 重构路线，建议先落地 P0-P1 的局部优化（正确性修复 + 热路径加速），再推进 P3 的结构拆分。
